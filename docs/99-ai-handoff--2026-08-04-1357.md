## Approved programming direction

- Use plain HTML, CSS, and JavaScript unless a demonstrated need justifies more.
- Target `index.html`, `styles.css`, `assets.js`, `game.js`, `ui.js`, and
  `app.js`. Three to four JavaScript files are preferred; `ui.js` and `app.js`
  may be combined if clearer.
- Do not create an army of tiny modules. Add a file only for a distinct concern
  that has become difficult to read or test, and review a larger architecture
  with John first.
- Prefer meaning-oriented names with units where helpful. Conventional `x`,
  `y`, `index`, and `counter` are fine in obvious small scopes.
- Use section dividers and comments that explain intent, invariants, and
  non-obvious edge cases rather than narrating syntax.
- Keep one explicit serializable state tree, pure/testable game rules, DOM-free
  transitions, derived score selectors, and one-time effects.

## Approved patient-data boundary

- Load and validate the canonical schema 2.2 JSON records from
  `patient-data/patient-json/` and index them once by ID.
- Retain the exact authored property names, casing, nesting, and values. Do not
  flatten or rename patient records into a second runtime schema.
- Waiting/active state uses small records such as
  `{ patientId, waitingBackgroundKey }`.
- Assignment ledger records contain patient ID and game-owned result fields.
  They do not duplicate the complete patient record.
- Selectors/renderers read canonical paths such as
  `patientRecord.patient.presentation` directly.

## Approved loading flow

1. Make HOME interactive after critical lobby code/art loads.
2. While the player reviews settings, load and validate patient JSON, shared
   game artwork, and deck metadata.
3. On Start Shift, show blocking `PATIENTS ARE ARRIVING` status.
4. Fetch and decode the initial queue portraits plus a measured near-term
   reserve before anchoring the timer or RUSH scheduler.
5. During play, maintain a rolling portrait reserve ahead of the deck cursor.
6. Size that reserve through fastest-RUSH mobile-network testing; do not make
   all 160 portraits a startup requirement.

## Approved asset sequence

1. Build and visually approve the game with current high-resolution production
   art at current logical paths.
2. Make CSS own all rendered boxes, crops, fit, and alignment. JavaScript and
   layout must not depend on `naturalWidth`, `naturalHeight`, or source pixels.
3. After final CSS, rerun the asset audit at iPhone 16 Pro Max 3x, Full HD, and
   normal 3840 x 2160 desktop reference presentations.
4. Create representative trials under
   `triageRush/assets/_asset-audit-and-resize/resized-assets/` and obtain John's
   visual approval before batching.
5. Preserve checksummed high-resolution masters outside the runtime manifest,
   preferably outside the deployed web root.
6. Replace optimized runtime files at the same logical names/paths where
   practical; format/path changes belong only in the centralized manifest.
7. Change the production cache version and rerun loading, decode, alpha-edge,
   lettering, geometry, and visual-regression checks.
