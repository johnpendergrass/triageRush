## Phase 7 decisions that changed earlier plans (all in docs now)

- The Chart does NOT pause the clock (reading a patient costs shift time).
  Pause reasons are only `confirmation` and `document-hidden`. This means
  RUSH arrivals also continue while the chart is open.
- The clock starts after a 2-second acclimation delay once GAME appears;
  RUSH's start tick plays when the clock starts, not on screen entry.
- The final-countdown cadence: whole-second countdown ticks 10..1, extras at
  N-0.25/N-0.50 during the final five, and the last TWO seconds beat on
  every quarter as a run-in to the endDong.
- RUSH numerals pop centered on the middle of the patient image and expand/
  dissolve (scale 1.7, fade, slight blur) over ~500ms. RUSH-only; Triage
  gets the audio cadence but no numerals.
- The clipboard's metal clamp was replaced by a header row: PATIENT CHART
  left-justified, the LIVE shift clock (mirrors the header timer every
  second), then the red X. Retired clamp CSS is kept commented in styles.css.
- The staged burst second-arrival timestamp is LOGICAL game time
  (`state.shift.elapsedMs` based), so pauses freeze it.

- **Review the last shift from ER ENTRANCE (John, 2026-08-05)**: HOME should
  offer a way back into the most recently completed or early-ended shift's
  SHIFT REVIEW. This is NOT Resume Shift - the shift is over and unplayable;
  it only reopens its results. WHAT THIS COSTS: `resetToLobby` in game.js
  currently wipes the ledger, queue, and deck, so the results are gone the
  moment the player leaves review. Implementing this means keeping a
  `lastCompletedShift` snapshot (the ledger records plus mode, difficulty,
  player, timestamps, elapsed, and the final left-waiting count) OUTSIDE the
  live shift state, since the live state must still reset. Doc 9's Phase 8
  line "Return to ER Entrance clears completed runtime state" needs amending
  to except that snapshot. Quit This Shift must still leave NOTHING
  reviewable (doc 3 is explicit that quitting creates no review result).
  Phase 9 persistence should then carry the snapshot across a refresh.

- **Lo-fi "hospital PA" music filter (John, 2026-08-05, consider - NO decision
  yet)**: run the music (KING-FM or whatever the source ends up being) through
  a filter chain before playback so it sounds like it is leaking from a
  waiting-room ceiling speaker rather than playing vibrant. The Web Audio
  recipe is small and familiar: `createMediaElementSource(musicElement)` ->
  highpass ~400 Hz (kills the bass) -> lowpass ~3.5 kHz (kills the air) ->
  a gentle peaking boost around 1-2 kHz for the honky midrange -> optional
  WaveShaper for a touch of grit -> gain -> destination. Two or three tunable
  numbers; easy to expose later as a CLEAN / LO-FI switch.

  CORS IS VERIFIED OK (checked 2026-08-05). The StreamGuys/Icecast endpoint
  answers with `Access-Control-Allow-Origin: *` plus
  `Access-Control-Allow-Methods: GET, OPTIONS, HEAD`, so the stream may
  legally feed a Web Audio graph. This was the one thing that could have
  killed the idea — routing a cross-origin `<audio>` element through Web
  Audio requires permissive CORS AND `musicElement.crossOrigin = "anonymous"`;
  without them the graph outputs SILENCE with no error, a confusing bug to
  meet cold. Do not skip setting `crossOrigin`, and set it BEFORE `src`.

  Remaining risk when this is built: adding `crossOrigin` changes a currently
  working playback path, so re-test plain playback (John's browsers, desktop
  + iPhone) alongside the filtered sound. If a future stream swap loses the
  CORS header the same silence trap returns — re-check headers then. The
  standing fallback is locally hosted tracks filtered OFFLINE, which
  side-steps CORS entirely and pairs with the music-options item above (a
  static GitHub Pages host cannot proxy, so proxying is never an option).
